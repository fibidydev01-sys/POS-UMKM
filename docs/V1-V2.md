# POS UMKM — Roadmap V1 vs V2
**Tanggal:** 2026-05-29
**Prinsip pembagian:** V1 = owner sebagai satu-satunya user. V2 = buka pintu untuk kasir tambahan + fitur lanjutan.

---

## Premis Utama

**V1 bukan "fitur dikurangi" — V1 adalah "kompleksitas dikurangi."**

Schema DB sudah dirancang untuk V2 (multi-user, promo, RLS). Tapi V1 bisa berjalan di atas schema yang sama dengan menyederhanakan layer aplikasi, bukan mengubah DB. Artinya: tidak perlu dua schema berbeda. Upgrade ke V2 nanti cukup di application layer.

---

## V1 — Owner-Only POS

**Definisi:** Satu UMKM, satu perangkat, satu orang (owner) yang sekaligus juga kasir. Tidak ada login, tidak ada role, tidak ada pembagian akses.

### Yang Masuk V1 (beserta alasan)

#### 1. Fix Schema Alignment — Wajib, Tidak Bisa Ditunda

| Item | Alasan masuk V1 |
|---|---|
| **users table + system user seed** | `kasir_id`, `updated_by`, `void_by` semua FK NOT NULL ke `users(id)`. Tanpa ini, INSERT transaksi dan INSERT menu langsung gagal FK constraint. Di V1, cukup satu row per UMKM dengan role `'owner'` yang di-seed otomatis saat aktivasi. |
| **Soft delete menu item** | Schema melarang hard delete. Kode sekarang `.delete()` langsung → data riwayat korup. Bug ini harus diperbaiki sebelum app dipake siapapun. |
| **Fix kolom `transaksi`** | `nomor_order` perlu format `YYYYMMDD-XXXX`, `created_at` bukan `timestamp`, `status` enum wajib ada. Kolom ghost (`subtotal`, `diskon_persen`, `catatan`) akan bikin INSERT gagal di schema final. |
| **Fix kolom `transaction_items`** | `item_type` enum wajib diisi (CHECK constraint di DB). V1 cukup pakai `'normal'` dan `'discounted'` — `'promo_free'` belum dipakai tapi enum harus dikirim. |
| **Fix field `menu_item`** | `is_active` vs `is_available` berbeda makna di schema. `updated_by` NOT NULL. Harus benar sebelum flow kelola menu bisa jalan. |

#### 2. Payment Method — Wajib, Scope Dibatasi

**V1:** Cash + QRIS saja.

**Alasan masuk V1:** `payment_method` adalah enum NOT NULL di schema — tidak bisa null atau string bebas. Minimal satu nilai valid harus dikirim. Cash cover mayoritas UMKM kecil. QRIS sudah menjadi standar de facto Indonesia, tidak masuk akal dikecualikan.

**Alasan debit + transfer masuk V2:** Flow keduanya butuh nominal konfirmasi dan rekonsiliasi yang lebih kompleks di UI. Untuk MVP, tidak worth menambah kompleksitas keranjang.

**Catatan khusus cash:** Schema punya CHECK constraint — kalau `payment_method = 'cash'`, maka `uang_diterima` dan `kembalian` WAJIB ada dan konsisten. Ini tidak bisa di-skip. Jadi di V1, keranjang harus ada input "uang diterima" untuk transaksi cash, dan kalkulasi kembalian real-time.

#### 3. Diskon Preset — Wajib, dengan Pendekatan Pragmatis

**V1:** Seed 4 preset default saat aktivasi (5%, 10%, 15%, 20%) + halaman CRUD preset di pengaturan.

**Alasan masuk V1:** Schema melarang diskon nominal bebas. `transaction_items.diskon_preset_id` harus FK ke `diskon_preset(id)` jika ada diskon — tidak ada jalan lain. Kalau diskon preset tidak ada, kasir tidak bisa mendiskon sama sekali.

**Kenapa tidak cukup hardcoded?** Owner UMKM punya kebijakan diskon berbeda-beda. Ada yang hanya pakai 10%, ada yang sampai 30%. Preset hardcoded di kode = tidak fleksibel, harus update app untuk ganti diskon.

**Solusi pragmatis V1:** Seed default saat aktivasi sehingga app langsung bisa jalan, owner bisa edit/tambah dari halaman pengaturan.

#### 4. Void Transaksi — Wajib

**V1:** Owner bisa void transaksi (status → `'void'`). Tanpa reason wajib — cukup konfirmasi.

**Alasan masuk V1:** Owner tetap butuh cara koreksi kalau ada salah input. Kode sekarang pakai hard delete — ini harus diubah ke void karena schema punya `status` enum dan audit trail. Hard delete transaksi yang sudah ada item-nya juga bisa trigger cascade yang tidak terkontrol.

**Kenapa refund masuk V2:** Refund semantiknya beda (uang kembali ke pembeli, butuh flow kasir konfirmasi, butuh catatan nominal). Untuk owner-only MVP, void sudah cukup.

#### 5. Export / Import Excel — Masuk V1

**Alasan:** Sudah ada di codebase, hanya perlu fix mapping kolom sesuai schema. Backup manual adalah satu-satunya safety net untuk UMKM yang tidak paham cloud storage. Buang ini dari V1 = meningkatkan risiko kehilangan data.

#### 6. Disable RLS — Keputusan Sadar untuk V1

**V1:** RLS di-disable. Isolasi tenant tetap via `.eq('umkm_id', ...)` di setiap query.

**Alasan:** RLS yang ada di schema menggunakan session variable `app.current_umkm_id`. Supabase JS client dengan connection pooler tidak menjamin session persistence antar request — session variable bisa reset kapan saja. Tanpa Supabase Auth, tidak ada mekanisme reliable untuk set session variable ini. Memaksakan RLS tanpa auth yang benar = app tidak stabil (query tiba-tiba return kosong).

**Trade-off yang diterima:** Jika ada bug di application layer yang menyebabkan `umkm_id` salah, bisa terjadi data leakage antar tenant. Risiko ini acceptable untuk V1 karena: (a) scope masih kecil, (b) semua query sudah pakai `.eq('umkm_id', ...)` secara eksplisit, (c) V2 akan benar-benar fix ini dengan Supabase Auth.

**Yang perlu didokumentasikan:** RLS disable adalah utang teknis yang harus diselesaikan sebelum scale.

## V2 — Multi-User + Fitur Lanjutan

**Definisi:** Owner bisa tambah akun kasir. Setiap kasir login dengan username/password. Owner punya akses penuh, kasir akses terbatas. Fitur promo otomatis mulai aktif.

### Yang Masuk V2 (beserta alasan)

#### 1. Multi-User / Login Kasir

**Komponen:**
- Halaman login (username + PIN / password)
- Manajemen user di pengaturan (tambah kasir, nonaktifkan kasir)
- Session per user (bukan per UMKM)
- `kasir_id` di transaksi mulai bermakna — bisa filter "omzet per kasir"

**Alasan ditunda ke V2:** Menambahkan auth layer adalah perubahan fundamental yang menyentuh hampir semua bagian app. Di V1, owner adalah satu-satunya user sehingga tidak ada kebutuhan diferensiasi. Memaksakan auth di V1 hanya akan menambah friction (login setiap buka app) tanpa nilai tambah.

**Dependency V2:** Perlu Supabase Auth atau sistem token custom. Ini juga jadi prerequisites untuk mengaktifkan RLS kembali.

#### 2. RLS Proper dengan Supabase Auth

**Komponen:**
- Migrasi dari cookie `umkm_id` ke Supabase Auth JWT
- JWT claim `umkm_id` di-set saat login
- RLS policy pakai `auth.jwt() -> 'umkm_id'` bukan session variable
- Hapus semua `.eq('umkm_id', ...)` manual — RLS yang handle

**Alasan ditunda ke V2:** Bergantung pada item #1 (auth layer). Tidak bisa dikerjakan terpisah.

**Kenapa penting di V2:** Ini adalah satu-satunya cara isolasi tenant yang benar-benar secure. V1 masih aman selama tidak ada bug di application layer, tapi tidak ada jaminan structural.

#### 3. Promo Rule (BOGO / Buy2Get1)

**Komponen:**
- `src/lib/db/promo-rule.ts`
- `src/lib/cart/promo-engine.ts`
- `src/app/pengaturan/promo/page.tsx`
- `src/components/pengaturan/form-promo-rule.tsx`
- Update `simpanTransaksi` untuk handle `item_type = 'promo_free'` dan `triggered_by_item_id`

**Alasan ditunda ke V2:** BOGO/buy2get1 adalah fitur advanced yang tidak semua UMKM kecil butuhkan. Kompleksitas implementasinya cukup tinggi — terutama `triggered_by_item_id` yang FK ke `transaction_items(id)` sendiri, memaksa INSERT sequential bukan batch. Untuk MVP, risiko bug ini lebih tinggi dari nilai yang diberikan.

**Catatan schema:** Schema sudah siap. `item_type` enum, `triggered_by_item_id`, tabel `promo_rule` — semua sudah ada. V2 tinggal mengisi, tidak perlu migrasi DB.

#### 4. Payment Method: Debit + Transfer

**Komponen:**
- Tambah pilihan Debit dan Transfer di UI keranjang
- Tidak ada constraint tambahan di DB (enum sudah include keduanya)
- Mungkin butuh: input nomor referensi untuk transfer, nama bank untuk debit

**Alasan ditunda ke V2:** Cash dan QRIS cover kebutuhan mayoritas UMKM kecil. Debit dan transfer lebih umum di warung yang sudah lebih besar atau punya kasir khusus — lebih relevan setelah ada multi-user.

#### 5. Refund Flow

**Komponen:**
- Status `'refund'` di enum transaksi
- UI konfirmasi refund (beda dari void — ada nominal refund yang dikembalikan)
- Laporan refund terpisah di dashboard

**Alasan ditunda ke V2:** Refund membutuhkan konteks kasir (siapa yang approve, siapa yang terima uang kembali) yang lebih relevan setelah ada multi-user. Di owner-only, void sudah cukup untuk semua kasus koreksi.

#### 6. Laporan Per Kasir

**Komponen:**
- Filter di dashboard: omzet per kasir
- `kasir_id` mulai dipakai untuk analisis, bukan hanya FK formalitas

**Alasan ditunda ke V2:** Tidak ada nilai kalau hanya satu user. Baru berguna setelah ada kasir tambahan.

## Perbandingan Ringkas

| Aspek | V1 | V2 |
|---|---|---|
| **User model** | 1 user per UMKM (owner = kasir) | Multi-user, role owner vs kasir |
| **Auth** | Tidak ada login. Cookie `umkm_id` sebagai identitas tenant | Login username + PIN/password |
| **RLS** | Disabled. Isolasi via `.eq('umkm_id',...)` | Enabled. Isolasi via JWT claim |
| **Diskon** | Preset (seed default + CRUD owner) | Sama |
| **Promo** | Tidak ada (schema ready, engine belum) | BOGO + Buy2Get1 |
| **Payment** | Cash + QRIS | + Debit + Transfer |
| **Koreksi transaksi** | Void (owner only) | Void + Refund |
| **Laporan** | Per UMKM | + Per kasir |
| **`kasir_id`** | Ada (system user), tidak bermakna | Bermakna — siapa yang transaksi |
| **`item_type`** | `normal` + `discounted` saja | + `promo_free` |
| **Export/Import** | Ada | Ada (tidak berubah) |

## Utang Teknis yang Harus Diselesaikan Sebelum V2

Tiga hal ini bukan fitur baru — ini perbaikan fundamental yang harus selesai sebelum V2 bisa dimulai:

1. **Supabase Auth integration** — Cookie `umkm_id` tidak bisa dipakai sebagai auth untuk multi-user. Perlu migrasi ke auth yang sebenarnya. Ini prerequisite untuk semua fitur V2.

2. **RLS re-enable** — Setelah auth ada, semua policy RLS perlu diupdate dari `app.current_umkm_id` ke `auth.jwt()->'umkm_id'`. Ini perlu SQL migration, bukan hanya code change.

3. **`kasir_id` tracking yang proper** — Sekarang V1 pakai satu system user. Setelah multi-user, perlu mekanisme "siapa yang sedang login" yang konsisten di seluruh app — termasuk `void_by` yang berbeda dari `kasir_id`.

## Kapan V1 Selesai?

V1 selesai ketika:
- Owner bisa tambah menu, set harga, toggle ketersediaan
- Owner bisa terima bayaran (cash dengan kembalian, QRIS tanpa kembalian)
- Nomor order keluar dengan format benar
- Owner bisa void transaksi yang salah
- Riwayat menampilkan status (completed / void) dengan benar
- Dashboard omzet hanya hitung transaksi `completed`
- Backup Excel bisa didownload dan di-restore
- Tidak ada data yang korup akibat hard delete atau kolom yang tidak match schema
